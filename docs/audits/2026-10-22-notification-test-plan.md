# サービスを停止しない通知到着試験

2026-10-22。ユーザーが試験ルール作成・試験通知・一時ルール後片付けを承認。以下は計画と実行証跡を区別して記録する。

## 方法の選定

Cloud Monitoring公式資料では、メール通知チャネル単体のテスト機能はなく、条件を満たすアラートポリシーによる確認を案内している。VMのCPUを使う例もあるが、この試験ではVMを作成せず専用ログを使う。

- 対象プロジェクト：`construction2nd`。
- 通知先：既に承認済みのメール通知チャネル1件を再利用。アドレスは文書へ保存しない。
- 新規作成：試験専用の一時ログ一致ルール1件。
- 入力：個人情報・決済情報を含まない試験ログ1件。`resource.type="global"`、専用logName、実行ごとのrunId、固定メッセージの完全一致で対象を限定。
- 通知表示名：`[TEST] 電工2種サクサク道場 通知到着確認`。
- 説明文：通知到着の試験であり、サービス障害ではない。アプリ・決済・教材は停止していない。
- 通知間隔の下限：300秒。自動クローズ：1800秒。OR条件1件。

専用ログ名は `construction2nd-notification-test`。既存の決済例外フィルタが要求するCloud Runリソースと例外文字列を使わず、既存のサイト/API監視にも失敗を起こさない。小量のログと一時アラートルールの利用であり、完全無料とは断定しない。

作成要求・ログ要求は `/tmp/construction-notification-test-plan.json` にローカル準備。これはGitに保存しない。認証やAPIの呼出しコードは含まず、作成要求を準備しただけで外部サービスへ接続しない。

## 承認後の実行順序

1. 現在の承認済み通知チャネルが有効であることと、既存3ルールの状態を読み取り、試験前の比較用情報を確保する。
2. 一時ルールを作成し、返されたIDをローカルに記録。チャンネル、専用フィルタ、runId、期間、enabledを読み戻す。作成要求がタイムアウト等で不明なら、新規作成を繰り返さず有無を調べる。
3. ルールの反映を待ってから試験ログを1件送る。送信結果が不明でも自動で再送しない。ログとアラートの生成状況を確認してから次を判断する。
4. ユーザーに受信トレイ/迷惑メールで試験名のメールを確認してもらう。生成されたアラートやログ受信だけでメール到着済みとはしない。
5. 届かなければ、ログ一致、通知チャネル、通知配信エラー、迷惑メール等を切り分ける。既存の本物の障害を起こして試さない。
6. 届いた場合も届かない場合も、検証終了時に**今回作った一時ルールだけ**をGETで照合し、無効化・削除して不在を確認。既存3ルールと通知チャネルが試験前から不変であることを照合する。中断した場合は残存する一時ルールのIDと状態を記録し、後片付けを完了扱いしない。

一時ルールの削除は試験計画に含むが、実行承認を得る前には行わない。試験ログや操作監査ログは実設定の保持に従って残り得る。プロジェクト全体のログを消す後片付けはしない。メール件数や到着時刻は保証せず、追加通知が来た場合も記録する。

## この試験で確認できること・できないこと

- 確認対象：同じMonitoringメールチャネルを使う試験アラートの生成と本人メールへの到着。
- 対象外：実際のサイト/API停止の検知条件、決済関数からの例外ログ出力、Stripe通知未着、費用予算のロール通知の実到着。
- 既存の監視条件や対象アプリを変えないため、この試験だけで3本の本番障害経路をすべて確認したとはしない。
