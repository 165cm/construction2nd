更新：2026-10-22。基本方針は [規約・表示セット](DRAFT_POLICY_PACK.md) の6項目を正本とする。
この文書は手順案であり、実施済み・一般販売可能・法的確認完了を意味しない。公開、契約停止、返金、データ削除は実施していない。

## 1. 販売者情報の請求時開示

2026-10-22本人回答：正式情報は手元の非公開の場所に用意でき、請求への対応も本人が行う。これは準備可能・担当の確認であり、実情報の用意済み確認や開示フローの試験完了ではない。

### 公開前の成立条件

- 正式氏名、現に活動する住所、確実に連絡できる電話を運営者が用意する。屋号だけでは代替しない。実情報は公開リポジトリやチャットへ記入しない。
- 特商法ページから、購入前・ログイン前にも請求できるメール窓口へ到達できるようにする。「請求に応じ遅滞なく提供する」旨を表示する。
- 購入判断に十分先立って必要事項を実際に返せる担当・受信確認・送信方法を用意する。一般問い合わせの「原則2営業日以内」は、開示要件を満たす法定期限ではない。
- 販売者情報を求めるだけの人に、学習記録削除と同じ本人確認や購入・ログインを一律に要求しない。
- 実情報を扱わない模擬文面で、外部からの請求受付→担当確認→返信先選択→必要事項の提供→到着確認を通す。送信は本人が行うか、対象と内容を明示して許可を受ける。
- 差出人の個人情報対策はユーザー指示で保留中。請求された正式情報の意図的な提供と、通常の問い合わせ返信で個人情報が露出する問題は別に扱う。

### プライバシー側の確認

特商法の省略条件だけで個人情報保護法上の公表事項を満たすとは扱わない。事業者氏名・住所（法人は代表者）、利用目的、開示等の請求手順・定めた場合の手数料、安全管理措置、苦情窓口、該当する認定団体の情報を、本人が知り得る状態にする方法を別途確認する。求めに応じて回答する方法を使う場合も、実際に遅滞なく回答できることが必要。

## 2. 問い合わせと支払い反映遅延

採用済み：土日祝を除く原則2営業日以内の最初の返信が目標。解決期限ではない。

1. 問い合わせを「販売者情報の請求」「個人情報の請求」「支払い/利用不能」「教材/その他」に分ける。同じメール窓口でも必要な対応は分ける。
2. 支払済み利用不能では、重複購入を案内せず、同じGoogleアカウントか・利用期限・「支払い・利用期限を再確認」の結果を確認する。
3. 最小限の決済照合情報だけ受け取り、対象環境・購入と利用権・通知処理を照合する。カード番号・セキュリティコード・パスワードは受け取らない。
4. 調査状況と次の連絡予定を返信する。復旧できない場合は採用済み返金方針へ進む。

通常の問い合わせ履歴は対応完了後の再問い合わせ用に最長1年保存し、不要なら早めに削除する（2026-10-22採用）。未解決の請求/紛争と法令上保存が必要な記録は区別する。Google Groupsと各受信者のメール等に残る写しの対象・削除方法は [問い合わせ履歴の削除手順案](SUPPORT_RETENTION.md)。6か月点検と1年上限の期限管理は分ける。実保管先/権限/模擬削除試験を確認するまで、実施済みとは扱わない。

要準備：担当者、受信確認を続けられる体制、長期不在時の代替、復旧不能と判断する手順。具体的な期限を追加する場合は未採用案として確認する。

## 3. 返金（実行前に対象を確定）

採用済み：購入者都合は原則返金なし。重複分は返金。不具合はまず復旧し、運営原因で利用不能を解消できなければ該当支払いを全額返金。法令上必要な対応は別途行う。

1. 依頼者と対象の関係を確認し、テスト/本番、UID、Stripe顧客、支払い・請求書、返金済み額、対応利用権を照合する。問い合わせメールだけを根拠に別人の契約を操作しない。
2. 重複請求では「残す支払い」と「返す支払い」を区別。不具合では復旧対応と利用不能の事実、返金対象の支払いを記録する。
3. 金額、対象、利用終了への影響、月額更新の扱いを説明して操作承認を得る。
4. Stripeの返金結果→通知処理→対象支払いの失効→アプリの利用状態を確認。他の支払済み権利と学習記録が変わっていないことも確認する。
5. 月額の返金と自動更新停止は別操作。返金だけで以後の請求が止まるとは案内しない。更新停止が必要なら対象契約を別途確認し、停止結果を照合する。

**現実装の制約**：一部返金でも対象支払いの利用権全体が失効する。日割りの期間短縮の代用にしない。支払いが複数ある場合、重複分の返金が残すべき有効権利を失効させないことを確認する。

追加決定（2026-10-22）：次回更新日時より前の解約完了、購入者都合の途中解約/未使用の日割り・残期間返金なし、不具合/重複請求の独自連絡締切なし（気付いた時点で連絡）を採用。自動返金の約束や法令上の期間変更ではない。

要確定：判断担当と復旧不能の基準、処理時期、返金時の利用終了・更新停止条件。本番Stripeの解約締切と画面表示は公開前に照合する。

根拠：`functions/index.js` の `revokeCharge` / `stripeWebhook`、`functions/billingPolicy.js`、[決済検証](../BILLING_SETUP.md)。

## 4. 学習記録の削除

採用済み：問い合わせで受付、本人確認後30日以内を目標に対応。保存の必要性を6か月ごとに見直し、不要と分かった情報は次の点検を待たず削除対応。請求・法令等のため保存が必要な情報は区別する。

1. 依頼内容を「クラウド学習記録のみ」「端末記録も含む」「アカウント自体」に分ける。
2. 対象UIDとログイン本人を結び付ける方法を整備する。メールアドレスの申告だけで削除しない。具体的確認方法は未整備であり、ここでは確定しない。通常の問い合わせに身分証画像を一律要求しない。
3. 対象は原則 `users/{uid}/learning/backup` のクラウド学習記録。利用権・認証・Stripe支払い/契約・問い合わせ履歴は別に説明し、削除対象と残す情報を確認する。
4. 対象と影響の承認後、管理権限で指定文書だけ削除し、不在を確認して完了連絡する。親の `users/{uid}` を一括削除したり、学習記録の削除に返金/解約を混ぜない。
5. 各端末の記録は管理者によるクラウド削除では消えない。端末側の削除方法と、再保存によりクラウド記録を再作成できる点を案内する。バックアップ等に別の写しがある場合はその反映方法・時期も確認する。
6. アカウント自体の削除を希望する場合は、月額更新停止、残期間、法令等で残す決済情報を別途整理する。

利用者側の削除API/退会画面はない。Firestoreルールも利用者からの削除は許可していない。上記は管理者の手動手順案であり、本人確認の仕組みを整備して試験するまで対応準備完了とはしない。

追加決定（2026-10-22）：記録の開示・削除等の受付対応は無料。本人確認は行う。

要確定：担当、本人確認方法、6か月ごとの点検方法、通常問い合わせ以外の情報別保存期間、外部サービス/バックアップの扱い。これらは方針であり、自動削除機能や定期実行は作成していない。

根拠：`src/services/cloudBackup.js`、`firebase/firestore.rules`。

## 5. サービス終了

採用済み：原則3か月以上前にサイト内告知と有料利用者へのメールで通知、新規購入・更新停止、購入済み利用期限まで提供。

1. 告知方法、告知日、購入受付停止日、予定終了日を運営者が確認する。通知メール等は送信内容と対象の承認を得る。
2. 新規購入の作成停止を稼働設定へ反映。発行済みの未払いCheckoutは別途洗い出して、承認した対象の失効と結果を確認する。
3. 既存月額契約の更新停止を別途実施する。アプリの購入ボタンを隠すだけ、あるいは購入停止フラグだけでは既存の更新は止まらない。
4. 停止中に決済・更新が完了したものや通知遅延を再照合。現在有効な権利だけでなく、将来開始する支払済み期間も確認し、全利用者の実際の最終期限以後を終了日にする。暦の3か月を90日で代用しない。
5. 最終期限までは教材・認証・利用権確認・契約管理・決済通知処理・問い合わせを維持する。売上受付を止めた時点で教材配信を止めない。
6. 終了後も必要な返金/個人情報請求への窓口と記録保持を整理してから、対象別の停止・削除を承認付きで進める。

要確定：告知表示とメール対象抽出・送信・到達確認の手順、担当、期限まで提供できない例外時の精算。運営原因で利用不能を解消できない場合は採用済み返金方針に従う。

根拠：[停止・復旧の監査](../audits/2026-10-21-release-operations.md)、`functions/billingPolicy.js` の `accessSummary`（現在有効な権利の集計）。
